# Specification — contextrover

**Methodology name:** Domain-Driven Modernization (DDM)
**Tagline:** Spec-driven development where the spec is discovered, not declared.

---

## 1. Purpose

`contextrover` is a CLI-agent plugin that drives **Domain-Driven Modernization**: re-decomposing N existing services into M bounded-context-aligned services with **no unadjudicated behavioral change**, while serving both legacy and new interface surfaces.

It supplies the stage that spec-driven development lacks — recovering an authoritative specification from a system that already works — and links every downstream artifact back to that evidence.

---

## 2. Prior art and the gap

*Embedded so the builder agent does not need to research. These conclusions are settled.*

| Category | Representative work | Why it does not solve this |
|---|---|---|
| Spec-driven development | GitHub Spec Kit (`Constitution → Specify → Plan → Tasks → Implement`) | Assumes intent exists and is authorable. No evidence-extraction stage. Correct to reuse downstream of the spec; cannot start the process. |
| AI test generation | Qodo Cover, Diffblue, TestSprite | Generate **unit** tests that pin *internal* behavior. In re-decomposition the internals are redrawn by design, so these tests are not merely useless — they are actively misleading. **They pin the wrong layer.** |
| DDD automation research | *Automating Domain-Driven Design: Experience with a Prompting Framework* (arXiv 2603.26244) | Finds LLMs identify theoretically valid boundaries but **fail to account for practical dependencies, coupling, and operational overhead** that human architects weigh. Confirms boundary decisions must stay human-adjudicated, and that empirical coupling data must be an input. |
| Automated monolith decomposition | Patent US 11,093,216 and related | Targets decomposition from a monolith, not re-decomposition of an existing distributed estate, and does not address behavior preservation or delivery. |
| Shadow / diff testing | Signadot and similar | Solves the *comparison* mechanic. Does not produce the inventory of what to compare, nor connect it to specification or rollout. |

**The gap this fills:** nobody links *evidence → specification → verification → rollout → retirement* with a single traceability spine, and nobody characterizes behavior at the **protocol boundary** — which is the only layer that survives an internal redesign.

Two design consequences follow directly and are non-negotiable:

- **DR1** — Characterization operates on HTTP and event payloads, never on language internals (from the test-generation gap).
- **DR2** — Boundary proposals are generated by agents but **adjudicated by humans**, with empirical change-coupling supplied as evidence (from the arXiv finding).

## 3. Requirements

### 3.1 Evidence layer (Stage 1) — the core

- **REQ-01** Produce an **Interface Inventory** covering synchronous endpoints *and* asynchronous streams (published and consumed). Endpoint-only inventory is a failure.
- **REQ-02** For each async interface, record schema, partition key, ordering guarantee, delivery semantics, retry/DLQ behavior, and known consumers with evidence source.
- **REQ-03** Produce a **Behavior Inventory** where every behavior receives a stable ID and cites its evidence location.
- **REQ-04** Produce a **Divergence Register**: every place two or more services differ on the same concept.
- **REQ-05** Produce a **maskability assessment** per interface: volatile fields, whether they can be masked, and a GO / NO-GO verdict. NO-GO blocks Stage 6.
- **REQ-06** Produce **change-coupling analysis** from commit history, as boundary evidence (per DR2).
- **REQ-07** Produce **call-sequence analysis**: repeated multi-call patterns, with frequency. These are the requirements for the new API.
- **REQ-08** Produce **Retirement Register v0**: every legacy interface with known consumers and a sunset-date placeholder.
- **REQ-09** Anything undeterminable is recorded as an explicit `unknown` with a reason. Never omitted, never guessed.
- **REQ-10** All Stage 1 agents are read-only (`tools: Read, Grep, Glob`) and run unattended.

### 3.2 Traceability spine

- **REQ-11** Every behavior ID propagates: `behavior → context → service(s) → surface → spec clause → characterization test → task → rollout check → retirement entry`.
- **REQ-12** Coverage is computable at any moment as *% of behavior IDs with a passing characterization test*.
- **REQ-13** The Build Stream (legacy-surface conformity) and the Consumer Migration Stream (new-surface adoption) report as **separate** metrics. A blended number hides which is stuck.
- **REQ-14** Lint detects: orphan behaviors, orphan domain elements, behaviors spanning >1 service, interfaces with no retirement entry.
- **REQ-15** Each behavior carries its ensemble agreement score.

### 3.3 Stage state and resumability

- **REQ-30** `.contextrover/state.json` records per stage: status, timestamps, gate results, artifact paths, operator identity.
- **REQ-31** Every stage is re-enterable. Artifacts are additive; IDs are stable across re-runs. Re-running Stage 1 must not renumber existing behaviors.
- **REQ-31a** **Identity resolution.** Matching a Behavior found in a later run to its existing ID is performed by `scripts/resolve-identity.py` — **deterministic, stdlib, never by an agent**, because T19 requires byte-identical IDs across consecutive runs and agent judgement is not reproducible. Algorithm, applied per candidate in order:

  1. **Anchor match** — same `interfaces[]` set, same `kind`, and same `evidence[0].locator` file path with the line number stripped. Exactly one existing match → reuse that ID.
  2. **Content match** — among existing Behaviors sharing the same `interfaces[]` set and `kind`, compute Jaccard similarity over lowercased alphanumeric tokens of `summary`, stopwords removed. Highest score ≥ 0.80 **and** unique → reuse that ID.
  3. **Otherwise** — issue a new ID from `state.json.counters.BHV`. Counters only increase; an ID is never reused, even after deletion.

  A Behavior present in an earlier run but not found in this one is **never deleted**. It is marked `status: "unconfirmed"` with `last_seen_run`, and removal requires a human Adjudication. Silent disappearance is how a preserved behavior is lost between runs.

- **REQ-32** `/rover-status` renders the spine coverage report and stage ledger **from local files only**, with no network access.
- **REQ-33** Every gate execution appends an immutable entry to `.contextrover/gates.jsonl` (append-only). This is the audit trail; regulated environments require it.
- **REQ-34** All working state lives under `.contextrover/` in the target repository. The plugin never writes outside it except when explicitly asked to generate source.

### 3.4 Ecosystem integration (adapters)

- **REQ-40** The **local filesystem is the single source of truth.** External systems receive *projections*.
- **REQ-41** Projection is **one-way** (local → external). Bidirectional sync is explicitly out of scope — it is the dominant failure mode of tools in this category.
- **REQ-42** Every projection is an **idempotent upsert** keyed by artifact ID stored on the external object (label, custom field, or page property `contextrover-id`). Re-projection updates; it never duplicates.
- **REQ-43** Adapters declare the MCP tools they require. If those tools are unavailable, the stage still completes and the projection is recorded as `pending` — never a hard failure.
- **REQ-44** **No adapter is required for the framework to function.** Fully air-gapped operation is supported and must be tested.
- **REQ-45** Ship connector definitions for: issue tracker, wiki/docs, version control. Observability and chat are deferred to v2 (`12-extension-seams.md` §2); the connector interface is already generic, so no seam is required. Adapters are thin mapping specs, not integrations — the MCP server does the work.
- **REQ-45a** *(deferred to v2 — `12-extension-seams.md` §4; recorded here so the rationale is not lost)* A **Contexture export adapter**. [trustbit/Contexture](https://github.com/trustbit/Contexture) (MIT) is a Bounded Context Canvas wizard for capturing and visualizing a target context model. It documents *where you want to be*; this framework does the archaeology and delivery to *get there*. The two are complementary, not competing.
  - Export Stage 2 output (contexts, aggregates, ubiquitous language, context relationships) into Contexture's JSON snapshot format via its documented `PUT /api/all` endpoint, or to a file for manual import.
  - This is a **file-based export**, not an MCP adapter — no server dependency, works air-gapped.
  - Position it in the README as an integration, and credit Contexture explicitly. The Bounded Context Canvas is established prior art and adopting its vocabulary makes the Stage 2 artifact legible to anyone who already knows it.
- **REQ-46** Projection mapping:

| Artifact | Projects to | Why |
|---|---|---|
| Stage tasks | Issue tracker epics/stories | Delivery tracking where the team already works |
| **Divergence register entries** | Issue tracker, one per entry needing a decision | **The critical one.** Each divergence needs a named human owner; an issue is how that gets one. |
| PRD, ADRs, design doc | Wiki pages | Review and durable reference |
| Retirement register | One tracked issue per interface, with sunset date | Otherwise the legacy surface silently becomes permanent |
| Observability spec | Monitor/dashboard definitions | Day-zero observability, actually provisioned |
| Gate results | Chat notification | Makes objective gates socially visible |

- **REQ-47** Projection is always an explicit operator action (`/rover-project <adapter>`), never automatic on stage completion. Writing to external systems is a side effect and must be deliberate.

### 3.5 Language packs

- **REQ-50** Language specifics live only in `packs/`. Only Stages 1, 6 and 7 consult a language pack; Stages 0, 2, 3, 4, 5 and 8 contain zero language-specific content.
- **REQ-51** Ship packs for Java, Go, Python behind a documented pack interface.
- **REQ-52** Each pack supplies: sync route discovery, async binding discovery, behavior-extraction hints, arch-fitness tooling, characterization harness conventions, build/CI integration.
- **REQ-53** Source and target language are independent. Polyglot estates are the normal case; a Java estate re-decomposing to Go must work with no special-casing.

### 3.6 Ensembles

- **REQ-60** Stage 1 runs K independent extraction passes (default K=3), varying **framing** — routes, tests, call sites — not only model tier.
- **REQ-61** Results partition into: found-by-all (auto-accept), found-by-some (triage), found-by-one (inspect — hallucination or the subtle miss).
- **REQ-62** Every ensemble emits a schema-valid **adjudication record**: candidate, which passes found it, decision, rationale, decider.
- **REQ-63** No ensembles from Stage 7 onward. The harness is the oracle.

### 3.7 Guardrails and distribution

- **REQ-70** Ship `constitution.template.md` with placeholders only. `constitution.md` is gitignored from the first commit.
- **REQ-71** Missing constitution produces an actionable Stage 0 error, never a silent default.
- **REQ-72** Ship two permission profiles: `discovery` (read-only, `dontAsk`) and `authoring` (main session).
- **REQ-73** Scripts use Python standard library only. No installs, no network.
- **REQ-74** MIT license.

## 4. Non-goals

- Generating target service implementations. The plugin produces evidence, specs and harnesses; implementation is ordinary SDD downstream.
- Replacing Spec Kit. Hand off cleanly after Stage 5.
- Bidirectional sync with external systems (REQ-41).
- Deciding bounded contexts autonomously (DR2).
- Runtime traffic capture or replay infrastructure. The plugin specifies what must be captured; capture is platform work.

---

## 5. Whole-plugin acceptance criteria

The build is complete when all of the following hold:

1. `/rover-init` fails with an actionable message when `constitution.md` is absent, and succeeds when present.
2. Running Stage 1 against any sample repository produces schema-valid artifacts under `.contextrover/`, with stable IDs across two consecutive runs.
3. `python3 scripts/trace-lint.py` exits non-zero on a seeded orphan behavior and zero on a clean inventory.
4. `/rover-status` renders coverage and stage ledger with no network access.
5. Every agent file declares `tools` explicitly; no discovery agent declares a write or execute tool.
6. `grep -ri` across the repository finds no organization names, internal hostnames, topic names, or endpoint paths.
7. All three language packs implement every section of the documented pack interface.
8. A full stage sequence completes end-to-end with **no adapter configured** (REQ-44).
